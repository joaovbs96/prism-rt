# Hydra material support

The material service (`prism::materials::MaterialService`, `src/materialx/material_service.cpp`) reads `HdMaterialSchema` networks: `hdPrism` hands it the scene index's material prims, and the standalone CLI (`src/mesh/usd_mesh.h`) each bound material's composed UsdShade network, converted to the same schema (`HdUtils::ConvertHdMaterialNetworkToHdMaterialNetworkSchema`, under the `mtlx` context), so both front ends compile, fold, template and cache materials the same way. The service does not reopen the USD stage. It prefers the `mtlx` render context. When only the universal context is present, it accepts `UsdPreviewSurface` networks and translates the USD surface, texture, transform, and UV-reader nodes to the installed MaterialX USD definitions before using PrismRT's existing MaterialX-to-MDL compiler and CPU shading path.

The initial Preview Surface path covers the installed definition's common surface inputs and connected `UsdUVTexture` channels, including RGB color, scalar roughness/opacity channels, UV primvar readers, and `UsdTransform2d`. Texture assets are resolved through USD's resolver, using the resolved path carried by `SdfAssetPath` where available. Resolver-backed bytes are copied into the renderer cache so MDL can load them as local resources. `wrapS`/`wrapT` repeat is translated to MaterialX's `periodic` mode. Only the renderer's first UV set is available to MDL shading; arbitrary primvars and additional UV sets remain unsupported.

Converted MaterialX documents and texture resources live in the process temporary directory under `prism-rt/hydra-materials`. Cache keys include the converted graph, MaterialX library paths, and texture contents, so graph or image edits produce a new compiled material. Scene synchronization captures owned MaterialX documents and resolved resource paths before scheduling bounded parallel workers. Each compilation owns its transaction, execution context, generator and backend state. Identical content requests share an in-flight result. MDL class hashes allow compatible texture-free materials to share native target code while retaining separate argument blocks. Textured materials use instance compilation; failure to recreate a cached argument block regenerates target code. Cache access and native-code creation are synchronized independently of unrelated material work. Compiled materials are shared-owned and retained in a process-wide cache; the shared MDL context intentionally lives for the process lifetime to support repeated renderer creation and destruction.

An absent or unsupported network returns no material, allowing the geometry path to use display color or its neutral fallback. A network that reaches MDL but fails to load, generate, or compile is retained as PrismRT's visible magenta error material. Material resource, conversion, and compile problems are emitted through Tf warning diagnostics with the material path or asset name, so Hydra hosts can surface them. Configuration fallback messages and optional material-template debug output remain on stderr. The upstream Hydra MaterialX converter can warn about a Preview Surface normal texture's `color3` output; the service inserts the required conversion to the surface's `vector3` normal input before MDL compilation.

When an authored material is absent or fails resolution, meshes and spheres use the Hydra fallback material. Constant `displayOpacity` drives stochastic cutout on that fallback, including when no `displayColor` is authored; a resolved authored material takes precedence. Only constant display-color interpolation is supported for this fallback path; per-vertex and face-varying display colors are not.

Within a renderer, material paths are cached before network conversion and resource reads. Hydra material dirty notices invalidate those records; data-source wrapper pointer changes do not. A bounded process cache also retains owned network snapshots, resolver context, library paths, and resource revision across renderer recreation. Equivalent networks with unchanged filesystem dependencies reuse their materials before MaterialX conversion or texture-content hashing. Dependencies are resolved again and checked by path, file size, and modification time. Resolver-backed resources that cannot be validated this way bypass this early cache. `materialEarlyCacheHits` reports reuse separately from local path hits and compiled-content hits.

For texture files edited outside USD, increment `prism:resourceRevision` to invalidate material fingerprints and reload the dome without rebuilding geometry. This explicit reload also covers edits that retain a file's size and timestamp. Initial scene population preserves reusable process records; live material notices invalidate matching records. Invalidations prevent pending work from republishing obsolete conversion records.

The MaterialX loader references each worker's standard library instead of copying and validating its complete contents for every material. Documents that override a standard-library element retain the previous import behavior so authored definitions keep their precedence.

Opacity follows the current MDL material implementation's stochastic cutout behavior: each hit is accepted with the authored opacity probability, while a rejected hit continues the ray unchanged. This is coverage, not tinted transmission or physically based glass; transmission requires a material BSDF that supports it. Emission evaluation is weighted by opacity. Preview Surface features that the installed MaterialX definitions or existing MDL shading path cannot represent are not added by the Hydra adapter.

`tests/hydra/materials_test.cpp` compiles synthetic universal Preview Surface and MaterialX-context graphs, including a texture connected to color, normal, roughness, and opacity; it checks resolved relative texture loading, graph and image cache invalidation, and cache survival across service replacement. `tests/hydra/fixtures/parity.usda` and `preview_parity.usda` provide equivalent standard-surface and Preview Surface scenes for image comparisons.
