# Decisions

Design decisions and deliberate deviations, newest first. Each entry: date, decision, why.

## 2026-10-27
- **SDK step 1a: the internal context is `prism::RendererContext`** (`src/renderer/`), with `RendererOptions` and `RendererOptions::FromEnvironment()`; it becomes `Renderer::Impl` when the public API exists (step 3). `FromEnvironment` is the only reader of the API-level variables (OCIO, the MaterialX paths, the material compile policy and worker counts, the cache directory, the disabled devices); a default-constructed `RendererOptions` is the built-in defaults and nothing below the front ends reads those variables. Loader option structs of the front-end modules (`USDMesh::LoadOptions`) still default to the environment, as their subdivision defaults always did (row 11 stays a front-end helper).
- **One cache root**: `RendererOptions::cacheDirectory` (PRISM_CACHE_DIR), else `%LOCALAPPDATA%/PrismRT/cache`, else the temporary directory's `PrismRT/cache`. The material service's last fallback was `<temp>/prism-rt/materials` and is now `<temp>/PrismRT/cache/materials` (only without LOCALAPPDATA); with PRISM_CACHE_DIR or LOCALAPPDATA every path is unchanged.
- **Behaviour kept on purpose in step 1a**: the CLI still compiles with `<libraries>/mdl` as its MDL path (not PRISM_MATERIALX_MDL) and the Vulkan device's early texture uploads still use PRISM_GPU_TEXTURE_BUDGET_MIB (`DeviceOptions::initialTextureBudgetMiB`), not a render setting; `MaterialService` gained `SetCompileMode`/`SetParallelTexturePreparation` for tests that switch the policy between batches (they set environment variables before).
- **SDK step 1b: colour management belongs to the renderer context** (`RendererContext::colorManagement`/`setColor`); `prism::color::Active/SetActive/Activate` are gone. A `SceneManager` is created with the colour management it was loaded in and the devices read it from the scene (the CPU light selection, `GpuSceneData::luminanceWeights`, the light table). Loaders, materials and textures take it explicitly (`MaterialSettings`, `ImageTexture(path, space, color)`, `TexturePrepareOptions::colorManagement`, `MakeSceneLight`, the environments). The Hydra delegate sets its renderer's colour from its settings; a build job captures it at its start and drops a spare bank loaded in another working space. The delegate's environment cache keys by colour identity (its importance tables weigh texels by the working space's luminance). `prism_hydra_render` writes its images with the environment's colour management, as it did through its own copy of `Active()`.
- **SDK step 1c: the SSS fallback is a renderer material option, binding purposes belong to the delegate's snapshots.** `MaterialSettings::sssFallback` (from `RendererOptions::materials.sssFallback`, the CLI's flag and settings, the delegate's prism:sssFallback through `RendererContext::setSssFallback`) reaches `DocumentLoader` explicitly; `DocumentLoader`'s default is off and it reads no environment variable. Each Hydra snapshot records the material binding purposes of its settings and resolves bindings with them; a spare bank built with other purposes, another working space or another SSS fallback is not updated but rebuilt.
- **SDK decisions** (answers to `docs/sdk_design.md` section 8):
  - Errors are C++ exceptions (`prism::Error` with codes; Python exceptions). No C API before the first release.
  - Names: `prism::Renderer` / `Scene` / `Session`; the Python distribution and import name are both `prismrt` (submodules `prismrt.usd`, `.gltf`, `.obj`).
  - Several renderers per process are allowed (Hydra needs one per delegate instance, as HdPrman and Cycles do); shared cache keys are audited and tested (same material, two working spaces, one process).
  - Python honours the `PRISM_*` environment variables by default (`Renderer(env=False)` opts out); all of them are documented for now and filtered later.
  - One writer per scene plus `commit()`; mesh data copied at `commit()` in v1 (zero-copy shared buffers are a possible follow-up).
  - MaterialX stays out of the public C++ API: files and strings, plus a header-only helper that serialises a `MaterialX::DocumentPtr` in the caller's code; Python accepts `MaterialX.Document` objects. A built-in material preview (shaderball and default dome) renders a MaterialX document with no user scene.
  - Platforms: Windows, Linux and macOS from the start (development on Windows); Python 3.11+ supported, wheels built for 3.11 first.
  - USD in the Python package: option A — a private, internally namespaced USD inside `prismrt` (`PXR_SET_INTERNAL_NAMESPACE`/library prefix), so it coexists with any `pxr`; stages from the user's USD pass as files or exported layers. One more USD build to maintain; no in-memory stage sharing. hdPrism keeps using the host's USD.
  - Cancellation: a progress callback returning `False` and an explicit `cancel()`. Python's default device is `auto`. AOV names are the Hydra tokens next to the enum.
  - Order as planned (core + CLI, then Hydra, then Python). The first release with the SDK and Python is 0.2.0; the API freezes later (likely 1.0.0).
  - Licences for wheels: MDL SDK (BSD-3-Clause), DXC (NCSA; `dxil.dll` not shipped), vk_oidn and its weights (Apache-2.0) are redistributable with their notices. The Metal shader converter's terms are unknown (Apple's licence ships with its installer): open packaging item.
- **Domes follow UsdLux's lat-long orientation** (the OpenEXR convention in `usdLux/domeLight.h`: longitude 0 = +Z at the image's centre, +pi/2 = +X): PrismRT read longitude from +X, a quarter turn off (Typhoon's `usdlux/dome` grid: FLIP 0.883 -> 0.014). Fixed at the mapping (lookups and importance sampling, CPU and GPU), so USD domes, `--env` and the default dome all turn; textured-dome images change. The glTF/OBJ test environment `tests/gltf/studio_env.hdr` was regenerated rolled by a quarter (its generator now places its lights by UsdLux), so the tests it lights keep their lighting; the legacy references of QuadTest and `hydra_parity` were re-rendered (NRMSE 0.012-0.027 against the old ones, mean luminance within 0.04%). `DomeLight_1`'s `poleAxis` is still not read.
- **Rect light textures read upright from the lit side**: UsdLux's "a texture file's min coordinates should be at (+X, +Y)" is read as the first pixel (the data window's min, the top left, as the dome text uses it), which is how Typhoon renders `usdlux/visibleRect`; PrismRT had the image upside down.
- **triplanarprojection with tagged files: the first file's colour space converts the output** (as MaterialX's main branch now does), not each image separately: the generator converts such a node's output as a whole, and per-image conversion would need a graph rewrite; files tagged differently are logged.
- **EON's compensation is repaired only where it renders**: OpenPBR surfaces with a constant zero `base_diffuse_roughness` (the default) keep the library graph (libbsdf adds the lobe only above zero), so their images and program sharing are unchanged; a zero roughness is structural in material templates.
- **Undeclared shader inputs**: `open_pbr_surface`'s geometry inputs under `standard_surface`'s names are renamed (Typhoon renders `openPbr_bump_fractal`'s bump); other undeclared inputs are dropped with a warning rather than failing the material. `UsdPrimvarReader_matrix` (no MaterialX definition) becomes its fallback constant with a warning rather than the error material.
- **`UsdRenderSettings.renderingColorSpace` is honoured as the working space; the default stays ACEScg** (João's decision; Typhoon defaults to `lin_rec709_scene`). Precedence: `--working-space` > `prism:colorManagement:workingSpace` > `renderingColorSpace` > ACEScg, in both loaders. USD's linear names resolve through the OCIO config's aliases. **`data` (and `raw`, `identity`) render in linear Rec.709**: Typhoon says `data` "bypasses source color transforms"; PrismRT has no transform-free mode, and linear Rec.709 is where USD's untagged values and light colours live, so they reach the image as authored, the closest sound match; explicitly tagged inputs still convert (a raw mode would need the texture service, light and MaterialX paths to skip conversion, not worth it for a debugging setting). A non-linear or unknown token keeps ACEScg with a message rather than failing: the attribute is shared with other renderers.
- **The Metal device denoises with OIDN's own Metal device** (`oidnNewMetalDevice` on the render device's `MTLCommandQueue`, `oidnNewSharedBufferFromMetal` on the denoiser's shared, hazard-tracked `MTLBuffer`s), mirroring the Vulkan structure: a resolve kernel turns the accumulation into packed RGB colour/albedo/normal on the GPU, OIDN filters there, the host reads only the denoised colour; host images (the delegate) are written into the same buffers. Same library and weights as the CPU device, OIDN's own albedo/normal prefilters. The resolve kernel is a few lines of Metal Shading Language compiled at run time (`newLibraryWithSource`), not HLSL through DXC and Metal shader converter: no descriptor heap or cache for one tiny pass. Falls back to OIDN's CPU device on host copies when OIDN has no Metal device (logged once). Written on Windows, unbuilt: docs/gpu_devices.md has the Mac checklist.
- **OIDN on macOS is built from source with its CPU and Metal devices** (`tools/ci/build_oidn_macos.sh`, the same pinned source; ISPC 1.30.0's macOS universal tarball pinned as `oidn.ispc_macos_sha256`), against the oneTBB PrismRT links, as on Windows. OIDN's Metal device is off by default (`OIDN_DEVICE_METAL`), so a stock build or a package without it would leave the Metal device on the CPU fallback.
- **The CLI's `--env FILE` follows UsdLux** (radiance = texel × 2^`--env-exposure`), matching an untransformed DomeLight of the file at intensity 1, instead of the original `EnvironmentMap`'s extra factor of two (measured: exactly 2.0x the dome). `--env` renders are half as bright as before; `--env-exposure 1` reproduces an old render. `--env-color`, USD domes (CLI and Hydra) and the default dome already followed UsdLux and are unchanged. `EnvironmentMap` has no default multiplier any more, so no caller can pick up the factor by omission.
- **vk_oidn from NVIDIA's prebuilt SDK package, not built from source** (`tools/ci/fetch_vk_oidn.ps1`, v0.2.0 pinned with the package's SHA-256 in `tools/deps.json`), not a git submodule. Its Slang kernels need a `slangc` with `-denorm-mode-fp16` (vk_oidn's CMake checks it; tested with Vulkan SDK 1.4.363 / Slang 2026.17); our Vulkan SDK 1.4.321's `slangc` 2025.11 lacks the option, and the package needs only the Vulkan headers we already have: a static library (Release `/MD`, which RelWithDebInfo maps to) with the compiled kernels and the colour filters' weights embedded, so nothing new ships at run time. Its weights are OIDN 2.5.1's (oidn-weights 28883d17): packing our OIDN 2.5.1 source release's `rt_hdr_alb_nrm.tza` and `rt_hdr_calb_cnrm_large.tza` with vk_oidn's `pack_weights.py` gives byte-identical files to the embedded ones. The commits after v0.2.0 change only comments, docs and benchmarks.
- **The GPU prefilters the guides like OIDN's CPU device** (`prism:denoisePrefilter`, default on): vk_oidn has no albedo/normal-only filter, so the fetch script packs OIDN's `rt_alb`, `rt_alb_large`, `rt_nrm`, `rt_nrm_large` (from the OIDN source release, with vk_oidn's pinned `pack_weights.py`) and the build embeds them (`cmake/embed_files.py`); they run as vk_oidn LDR filters with custom weights: the albedo with OIDN's sRGB transfer, the normal with the linear one on `n * 0.5 + 0.5` (OIDN's own `snorm` mapping, done by a small pass before and after), the same models per quality as OIDN (`_large` for high, the base network otherwise). Without them the GPU's default output would be another image than the CPU's (prefiltering lowers the error by about 10% on the test room).
- **The Vulkan device enables vk_oidn's features only when the GPU has them all** (`shaderInt64/16`, 16-bit storage, `shaderFloat16`, the Vulkan memory model, `maintenance4`, subgroup size control; cooperative matrices when present) and otherwise falls back to OIDN's CPU device on host copies, saying so once (`PrismRT Vulkan: denoising ...`; the CLI prints the denoiser per denoise and in `[PrismProfile]`, the delegate in its `denoiser` stat). `PRISM_GPU_DENOISER=cpu` forces the fallback (and enables none of the features). The storage-image features vk_oidn's helper also sets are left off (PrismRT passes buffers).
- **Whole-image renders denoise their accumulation in place; the delegate uploads its host images.** The CLI path resolves the host-visible accumulation buffer on the GPU (sums times each pixel's 1 / samples, the same float product the host computes) into the denoiser's own RGBA buffers, denoises and reads back only the denoised colour. The delegate's accumulation lives on the host (part 1), so its denoise worker's images are uploaded; keeping progressive accumulation on the GPU is a separate change.
- **Denoising: OIDN 2.5.1 built from source with only its CPU device, against PrismRT's oneTBB** (`tools/ci/build_oidn.ps1`, pinned with source and ISPC 1.30.0 checksums in `tools/deps.json`), not Intel's prebuilt Windows package. Evidence: the prebuilt `OpenImageDenoise_device_cpu.dll` imports `tbb12.dll`, and the package ships oneTBB 2023.1 (`tbb12.dll` 2023.1.0; `oidnBenchmark -v 2` prints `TBB_header_interface_12190`); PrismRT (and OpenUSD, Embree) load oneTBB 2022.2 (interface 12160). Windows reuses a `tbb12.dll` already in the process, so the prebuilt device would run on an older runtime than its headers, which oneTBB does not support (only older binaries on newer runtimes); shipping its DLL instead would be a second, different oneTBB for the process. Our 2022.2 `tbb12.dll` does export every symbol the prebuilt device imports, so it might work, but unsupported. Built here: three DLLs (`OpenImageDenoise`, `_core` with the weights, `_device_cpu`), no `tbb*.dll`; the package script refuses one beside them and checks the package holds exactly one `tbb12.dll`. Optional at build time (`PRISM_ENABLE_OIDN`, ON when found). Our MSVC build runs as fast as Intel's (1080p high quality: 398 ms against 376 ms in OIDN's benchmark on this machine). Also checked: Intel's prebuilt DLLs with our 2022.2 `tbb12.dll` do run (436 ms), which is the unsupported combination we avoid.
- **The denoiser is the render device's** (`RenderDevice::CreateDenoiser`, `ImageRequest::denoise`): frontends never pick a backend, so vk_oidn (part 2) and OIDN's Metal device (part 3) replace the CPU fallback inside the devices. Whole-image renders denoise where the accumulation lives (the device, at the end of `RenderImage`); the delegate's progressive accumulation is on the host, so it hands host images to the device's denoiser.
- **The denoising normal is the shading normal at the albedo's vertex** (world space, through sharp bounces like the albedo, averaged over the pixel's samples), a fifth light AOV channel, not the geometric `normal` AOV (pixel-centre hit only: aliased, and not through glass). It rides in the `w` of the GPU's existing light AOV entries: no new storage, and renders without light AOVs are unchanged.
- **`--denoise none|aov|replace` in the CLI; `prism:denoise` true means `replace` there and "show the colour denoised" in the delegate**, whose raw accumulation (what `Map` and the colour products read) stays untouched. A `denoised` AOV/RenderVar is always denoised. Turning `prism:denoise` on or off restarts the accumulation (guides from its first sample); quality, prefilter and interval changes resume it.
- **The delegate denoises on its own worker thread** (one `std::thread`, coordinating only; OIDN's CPU device runs on the process's oneTBB): the render worker copies the means every `prism:denoiseInterval` passes and publishes finished denoises at pass boundaries, so it never waits for one, except for the final denoise at convergence, where it polls a stop every 2 ms.

## 2026-10-26
- **UsdLuxShapingAPI follows the 26.08 schema text literally** where it is precise: the cone, softness, focus and IES factors multiply; an applied API's fallbacks apply (the 90 degree cone limits sphere and cylinder lights to the front hemisphere); IES intensities are in candela without `normalize` (as the schema's formula reads), divided by the profile's mean intensity with it (the schema writes a product but says it preserves energy). Distant lights and domes ignore shaping. Shaping data rides in the light-alias buffer after the alias entries (no new binding, no larger `LightRecord`); IES profiles are resampled to 1-degree grids rather than kept on the file's angles (O(1) lookups; exact where the file's angles are whole degrees).
- **Motion blur waits until the SDK and Python API exist.** It changes how scenes are represented (time samples, velocities, shutter) in the layer the SDK will reshape, so it is built once on the SDK; the SDK design reserves time-sampled data, a shutter interval and per-sample time so adding it doesn't break the API. Next is Phase 8a (spotlights and IES), then the SDK.
- **The CLI compiles USD materials through the delegate's material service** (folded parameters, templates, caches), so both front ends share one material path and load at the same speed.
- **Surface repairs rewrite a private copy of the library graph, not the material** (`ClonePrivateGraph`/`PublishPrivateGraph` in `src/materialx/loader.cpp`): flattening the surface into the material made its internal constants (scatter modes included) class parameters, so the CLI's unfolded class programs kept every lobe variant (OpenPBR glass 3.5x, thin walls 7x the library's SPIR-V; cold Vulkan 412 s). A content-named nodedef and graph keep the constants literal and the node's inputs as the parameters, and are shared by every material with the same repair. Chosen over folding the CLI's parameters (that would end the CLI's program sharing across variants) and over a hand-written MDL implementation per repair (a second copy of each library graph to maintain). Float-level differences only (constant folding): albedo test values equal except 1e-4 in two tinted, sampled cases.
- **A thin wall whose backface shader is its surface compiles its scattering once** (equal slot hashes; CPU index and GPU dispatch alias the surface's function, from the surface's call site because DXC inlines each call): the second copy made thin-walled programs 1.9x larger. Identical code, identical images.
- **Vulkan shaders are checked and budgeted before the driver compiles them** (`PRISM_VULKAN_MAX_SPIRV_MIB`, `PRISM_VULKAN_DRIVER_MEMORY_MIB`): the driver's compiler runs in our process and ends it when it runs out of memory (OpenPBR playground: "LLVM ERROR: out of memory" with 16 large callables compiling at once), so concurrent DXC and driver compiles share a memory budget estimated from the shader sizes, and a shader too large for the machine falls back to the CPU device with a message instead of being handed to the driver. Slower cold compiles of scenes with very large programs (OpenPBR: 23 minutes under a 24 GB cap) are accepted over crashes; shrinking those programs is left for later.
- **Large MDL programs are two Vulkan callables, sample and evaluate** (`PRISM_VULKAN_SPLIT_PROGRAM_KIB`, default 1536 KiB of generated code): the driver's compile memory grows with the square of the SPIR-V size, so OpenPBR's 15 MB glass programs as 9 + 6 MB parts compile several at a time (cold OpenPBR 1468 s to 412 s, the same image). Small programs stay whole because a split program runs its MDL init twice when it evaluates (OpenPBR GPU time 0.83 to 0.96 s for 16 spp). The dielectric repair was left as is: none of the playground's programs uses `prism_dielectric_split`; its large programs are the coupled RT glass itself.

## 2026-10-25
- **Light AOVs split the colour by the first scattering vertex** (Cycles'/RenderMan's per-lobe convention, `C<RD>.*` / `C<RS>.*`): `emission` = light seen before any vertex (dome included, so the three add up to the colour without a fourth AOV); `diffuse` = MDL's `bsdf_diffuse` part at that vertex (diffuse transmission included) and subsurface entries; `specular` = the rest (glossy, delta, glass of any roughness). The split is the expected value of the lobe fractions of the sampled direction (the Phase 4 light-lobe machinery), not the sampled lobe's event type, so it needs no new MDL output and holds for MDL's stochastic lobe selection. LPEs other than the beauty's stay unsupported.
- **The albedo AOV is a per-sample estimate** (the BSDF sample weight) at the first non-sharp vertex, not MDL's auxiliary albedo function (no new generated code; converges with the samples; exact for Lambertian). "Sharp" = delta or BSDF sample pdf ≥ 1000/sr: MDL reports smooth OpenPBR glass and mirrors as glossy lobes, not specular events. Escaped paths give 0.
- **GPU cost is a kernel variant** (`PRISM_LIGHT_AOVS`), compiled the first time a render asks for light AOVs, so renders without them keep their kernel and images; the CPU checks a flag per contribution.
- **`Pworld` is the world-position AOV name** (`P` accepted as an alias, as RenderMan and Cycles call it); multi-part EXR is opt-in per product (`bool prism:exr:multiPart`), the default stays one part with every layer.
- **A thin-walled material whose back face emits what its front does is not a varying emitter when the front's emission is zero, and a varying cutout does not make zero emission vary** (`MDLMaterial::evaluateUniformEmission`, `backface_emission_matches_surface` from the compiled slot hashes). The CLI compiles each material as a class (parameters stay arguments), so the SDK cannot prove a thin-walled material's back face dark, and about 20 of the OpenPBR playground's materials counted as varying emitters (14 of them thin-walled): together with the real ones they went over the 2^20-triangle budget, so no varying emitter was a light and MEET MAT (a textured emitter) was only found by BSDF sampling. The delegate folds parameters and was under budget (225k triangles). Class compilation stays (templates need it); images of scenes under the budget do not change (chess, egg_gold, Teapot are bit-identical). `PRISM_MAX_VARYING_EMITTER_TRIANGLES` lowers the budget (for the `mtlx_emission` parity fixture), and going over it now prints a warning.
- **The CLI shares the delegate's mesh conversion and UsdPreviewSurface rewrite** (phase 7): `src/mesh/mesh_conversion.cpp` (subdivision, displacement, refinement budget, triangulation) and `src/materialx/preview_surface.h` were moved out of the delegate unchanged; each loader still reads the stage its own way (UsdGeom in the CLI, scene indices in the delegate). The CLI keeps its own polygon conversion for meshes that do not refine or displace, so its earlier images stay bit-identical; refined and displaced meshes use the shared one.
- **The CLI places every gprim on its own** (phase 7), as the delegate does, instead of one merged mesh: needed for light-link masks, instance primvars, per-prim primvars and ids. Polygon meshes stay in world space (bit-identical to before), prototypes are Embree instances.
- **The CLI reads USD materials from the composed UsdShade network first** (as the delegate), falling back to reading a referenced `.mtlx` file directly only when no network is composed: the direct read failed on the Teapot (material names) and the OpenPBR playground (relative texture paths in string MDL modules).
- **CLI fallback grey is the delegate's 0.5** (was 0.7) for geometry without a material or `displayColor`.
- **Prim ids are compared up to a renumbering** (`prism_compare_images --relabel`): each loader numbers its prims; element and instance ids compare exactly.
- **Textured emitters (Phase 5): the light sample looks the emission up with the footprint of the BSDF ray in its direction**, not at the finest texture level. MIS needs both strategies to estimate the same integrand; with the finest level, texture filtering of BSDF hits made the checker fixture's floor 6–10% too bright where black and bright texels meet.
- **Varying emission includes directional and cutout emission**, not only textures: a coated OpenPBR emitter (directional EDF) or an emitter with a varying cutout is now a light whose emission the light sample evaluates, instead of being left to BSDF sampling. Images of such scenes change (less noise; same expectation).
- **Triangles whose estimated emission is zero get no light record** (BSDF sampling only, still unbiased); a material's emission counts as zero when it is zero at the centres of up to 64 of its triangles on a placement. This probe also decides `SceneHasEmitters` (the default dome rule), so both agree. Other triangles weigh at least 10% of their material's mean.
- **Large light tables (over 4096 entries) pick lights with the white noise**, not the low-discrepancy selection number: on its 24-bit grid that number cannot select among a million entries with the table's probabilities, which biased MIS (pre-existing with many constant-emission triangles; OpenPBR's string lights). Scenes with such tables change (OpenPBR CLI mean −0.5%, closer to a BSDF-only reference); smaller tables keep their images bit for bit.
- **The estimate is capped** (2^20 triangles, about 4M evaluations: 1 to 16 stratified points per face) and reruns at each scene change; no cache yet.
- **CI paused until the repository goes public.** GitHub Actions stopped on billing; public repositories get free minutes.
- **UsdPreviewSurface rough glass is left as MaterialX builds it** (rough specular over smooth transmission). The UsdPreviewSurface spec says "the transmissive lobe (if any) always assumes roughness 0.0", so the alternatives that conserve energy (one rough lobe: frosted; a smooth lobe: drops the specular roughness) contradict it. The remaining energy loss is MaterialX/MDL's to fix. Comparison: `local/comparisons/usdps_glass/`.
- **The opaque layering loss (~4.6%) is not repaired.** No MDL construct reproduces OpenPBR's energy-conserving layering; a diffuse scale-up would be wrong at grazing angles and change nearly every material. Upstream only.
- **MaterialX upstream reports are held back** for now (list in the session memory; drafts in `local/upstream/`).
- **Process standards adopted from the gesso project** (CLAUDE.md "Working standards"; this file, `docs/PLAN.md`, `docs/PROGRESS.md`; subagent reports in `local/reports/`).

## 2026-10-24
- **Layered dielectric energy loss is repaired in `DocumentLoader`** where an exact construction exists (one reflect-and-transmit lobe, or MDL `fresnel_layer` over smooth transmission); everything else logs "only partly repaired". Proven independent of PrismRT with NVIDIA's `df_native` (`local/upstream/repro/`).
- **`main` is the reference.** `device-abstraction` was fast-forwarded into `main`; no separate reference branch. The `cpu-reference` device and the recursive `SceneManager::trace` were removed.
- **Legacy C++ materials removed**: the glTF legacy path, the hard-coded scenes, `Metal`/`Glass`/`Dispersive`, quads and boxes. Built-ins left: `Diffuse` (fallback), `Emissive`, `ErrorMaterial`.
- **OBJ/MTL → MaterialX `open_pbr_surface`**, following Adobe's USD file-format plugin mapping (reimplemented, cited in `docs/obj.md`); `disp` is converted to a displacement shader although the CLI doesn't displace yet.
- **A failed GPU image render is an error** (exit 1, no image, a descriptive message) instead of a black image.
- **The CLI lights a scene that has no lights, no constant-emission geometry and no `--env`** with USD's default dome (`--default-dome false` to opt out); Hydra uses usdview's default dome by the same rule.

## 2026-10-23
- **Adaptive sampling on by default:** max 2048 spp, threshold 0.01, minimum 64 samples (from a CPU study against 16384-spp references); no batch time limit by default; `prism:timeLimitSeconds` / `--time-limit`.
- **Env-var-only render settings promoted to `prism:*` settings with CLI flags** (precedence: flag > RenderSettings > env var > default).
- **glTF materials load as MaterialX `gltf_pbr` through MDL**; the `gltf_pbr` volume is connected by a loader repair (MaterialX leaves it unconnected).
- **usdview starts with "Enable Default Dome Light" on**; the delegate ignores it when the stage has its own lights.

## 2026-10-22
- **USD is built with OpenColorIO** (vcpkg's, one OCIO DLL for everything) and a patch for Hdx's OCIO 1D/2D LUT textures; usdview starts in the config's default view (ACES 2.0 SDR).
- **`prism:honorDoubleSided`, default off.**
- **PointInstancer `invisibleIds` keep compacted instance numbering** (deviation from the plan), because usdview's picking and selection use the compacted index.

## 2026-10-21
- **Dependencies:** OpenUSD 26.08, MaterialX 1.39.5, OpenSubdiv 3.6.1, OpenImageIO 3.1.14 (vcpkg), Python 3.11; `tools/deps.json` is the single source of versions.
- **Colour management:** ACEScg working space by default, ACES 2.0 SDR view for display and 8-bit outputs; EXR and AOVs stay linear. Untagged MaterialX colours are treated as working-space values (what MaterialX's generator does).
- **Two USD loaders are kept** (Hydra and the CLI) with CLI-vs-Hydra parity tests and a rule that features update both.
- **OpenPBR differences against the Arnold reference are not "fixed":** USD composition wins (a connection beats an authored value), and MaterialX's coat darkening of transmission is followed.
