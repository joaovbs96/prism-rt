# Decisions

Design decisions and deliberate deviations, newest first. Each entry: date, decision, why.

## 2026-10-30
- **The material service reads a network in its own order after editing it** (`src/materialx/ordered_network_interface.h`). `HdDataSourceMaterialNetworkInterface` lists an edited node's parameters and connections (and edited nodes and terminals) from a TfToken hash set, i.e. by token address, which changes between processes; hdMtlx builds inputs and nodes in that order, so the MaterialEggs countertop compiled differently ordered documents and rendered one of two images (about 1 run in 5, NRMSE 0.0026, sub-surface eggs). Names still in the unedited network keep its order and added names follow, sorted. Of the two images, the one most runs produced before is kept: networks that were never edited convert exactly as before, and the fixed countertop matches the majority image bit for bit; other scenes are unchanged. Chosen over sorting every document, which would have changed the images of all scenes, and over serialising the worker pool, which does not fix it (the order depends on token addresses, not on scheduling).
- **Vulkan read-only scene buffers go to device-local memory by default, inside one GPU memory budget with the textures** (`PRISM_GPU_SCENE_BUFFERS=auto|device|staging|host`; docs/gpu_devices.md, "Vulkan memory placement"). ReBAR memory (a host-visible type on the device-local heap) is written directly with `memcpy`, as system memory was: no staging, copies or barriers (host-coherent writes before a submission are visible to it); staging copies only without ReBAR; system memory otherwise. Textures keep priority: the buffers take VRAM only when the whole texture budget (and an estimate of the acceleration structures) still fits after them, else they stay in system memory. Rejected: computing the texture budget after placing the buffers, because a smaller texture budget changes images (lower resolutions) while the buffer placement never does, and `prism:gpuTextureBudgetMiB` is the user's setting. Measured on the RTX 4070 Ti, bit-identical images: OpenChessSet render time 0.52x of system memory (1.9x faster), MaterialEggs countertop 0.91x (median of 3 alternating rounds), with +298 MiB and +1562 MiB of VRAM.
- **Motion blur decisions accepted as recommended** (docs/motion_blur.md, Decisions): shutter [0,0] when none is authored; motion on when samples exist and the shutter is open (`disableMotionBlur` turns it off); interactive usdview blurs too; USD's velocity rule; at most 8 Embree time steps; moving emissive meshes left out of NEE for now; lights, dome and camera attributes other than the transform at one instant; Vulkan renders one instant per pass (not NVIDIA's motion extension); the pass time in a new `GpuFrame` field. Motion blur starts after the performance work, in fewer, larger stages than the plan's first draft.
- **Performance work first: batch 1 of the 2026-10-29 audit plus the render profiler, then batch 3 after profiling.** Cutout-aware shadow rays (batch 2) are acceptable because they converge to the same image (only noise differs, and the CPU then matches the GPU's opaque/non-opaque split); an option that makes images look worse would have to be off by default.
- **The CLAUDE.md commit rule stays Prism's** (agents commit locally; push, merge and PRs need João's approval), not the stricter rule of João's other project.

## 2026-10-29
- **Python API rough edges.** (1) `"depth"` stays normalised device depth; `"cameraDepth"` (`Aov.CameraDepth`) already worked as a string everywhere AOVs are accepted (`aovs=`, `result.aovs`, `result.aov`), so only the docs, the `Aov` docstrings and the examples changed. (2) The C++ API keeps `Sampled<Matrix4d>`; the Python layer reads a transform back friendlier without losing samples: `prismrt.matrix_at(value, time=None)` and `prismrt.Camera.transform(desc, time=None)` return a 4x4 (the only sample, else the one nearest `time`; several samples without a time raise `ValueError`), and `scene.params["<name>.transform" | ".camera_to_world"]` returns the 4x4 when there is one sample (it is written as a 4x4), the sample list otherwise. Description objects (`desc.transform`) are unchanged. (3) Names stay unique across kinds (2026-10-29 rule below); the clash error names the kind holding the name and suggests a suffix.
- **A `.mtlx` referenced into USD keeps its document `colorspace`, recovered from the composed stage and applied as parameter tags in the material service** (`src/usd/mtlx_color_space.h`; docs/materialx_compatibility.md, "Document colour space through USD"). usdMtlx stores `<materialx colorspace>` only as layer `customLayerData`, which composition drops, so both loaders read the document's untagged colours as ACEScg (0.104 normalized RMSE against the same network tagged in UsdShade; 0.20 for `two_materials.mtlx`'s red against `--material`). The space is read where the stage is still visible: the CLI from the Material prim's prim stack, Hydra through a UsdImaging API schema adapter for `MaterialXConfigAPI` (usdMtlx applies it to every Material) in hdPrism; both publish `prismMtlxDocument.colorSpace` on the material prim. The material service tags untagged colour and file parameters with it *before* capturing the network, so every network-keyed cache and the generated document's content key include it, and documents without a `colorspace` are untouched (bit-identical renders). Rejected: patching usdMtlx to author `colorSpace` metadata per input (a rebuilt OpenUSD for every machine and CI; the right upstream fix, to report later with the other MaterialX/USD issues); setting the attribute on the hdMtlx document after conversion (the network-keyed caches would not see it); a `DocumentLoader` repair (the document it gets no longer knows its source layer).
- **The preview selects the asset's `standard_surface` `material_model` variant, in a PrismRT-owned layer** (`resources/material_preview.usda`, which sublayers the unchanged asset; `MaterialPreviewScene()` opens it and `tests/hydra/fixtures/material_preview.usda` sublayers it). The asset's file default is `OpenPBRSurface`, but in that variant the `neutral` material (the ball's `core` and `base`, marked `# TODO` in the asset) has no `base_color` connection, so OpenPBR's default 0.8 applies and both rendered near white instead of the 18% grey with the "Material Preview" text (`maps/neutral.ACEScg.exr`) of the asset's `media/cover.jpg`. Its README calls standard_surface the default ("Autodesk Standard Surface (default)"). `sss_bars`, `uvgrid` and `box_base` connect `base_color` in both variants; the layer selects `standard_surface` on all three prims that carry the set (`materials`, `materials/examples`, `materials/box_base`) so the preview uses one model. One layer, not a session-layer edit in `LoadMaterialPreview`, so the CLI, Python and the Hydra parity fixture cannot differ. The stored `reference_marble.exr` was regenerated, since the preview's look changes by design (tolerances kept).
- **The built-in material preview is the USD-WG StandardShaderBall, its subdivision-surface variant, lit by the asset's own box and rect lights** (refines "a built-in material preview (shaderball and default dome)" below; `docs/material_preview.md`). João chose the asset and its `subdiv` geometry (a path tracer should exercise OpenSubdiv and displacement with it) and the asset's lighting. The asset has no HDRI or dome: its `environment.usda` is a closed, textured box (ACEScg EXR walls and floor) with two emitters of rect lights, so that is the lighting and usdview's default dome is not used. The files are shipped unchanged in `resources/shaderball` (9.9 MB: the scene, `layers/`, `material_surface_geo/subdiv.usda`, the example `.mtlx` files and `maps/` that its variants reference, `LICENCE`, plus our `ATTRIBUTION.md`; not the `triangulated` variant, README, media or sources), stored without line-ending conversion (`.gitattributes`: `-text`), attributed in README and NOTICE (CC BY 4.0).
- **The preview binds its material at load time, not in USD**: `prism::usd::LoadOptions::materialOverrides` (scene materials replacing the bindings of gprims under a prim path) puts the previewed `MaterialDesc` on `/standard_shader_ball_scene/shader_ball/material_surface`. A session-layer binding to a usdMtlx reference would need a file for string and `MaterialX.Document` input and would compile through the USD material path instead of `MaterialDesc`'s; with the override the CLI and Python pass the same `MaterialDesc` as `Scene.add_material`. One C++ entry point, `prism::usd::LoadMaterialPreview` (in `prism_usd`, as the scene is USD), serves `PrismRT --material` and `prismrt.preview_material`; MaterialX stays out of the public API (files and strings).
- **Several materials and no name: the first is previewed**, the rule `MaterialDesc::materialName` already has everywhere in the API; the CLI prints which one and the others, Python returns them. Errors are found before loading: a missing file and an unknown name are `NotFound` (the message lists the document's materials), an unreadable document or one without materials `InvalidArgument`. `--material` with `--scene`, `--camera*`, `--render-settings` or `--output-dir` is an error; the default resolution is 512x512 (the asset's camera is square).
- **The preview stage is found beside `prism_usd`** (`resources/shaderball` in the library's directory or one up; `PRISM_MATERIAL_PREVIEW_SCENE` overrides): the build copies it next to `prism_usd.dll`, `install` to `bin/resources` (`lib/resources` off Windows), the Windows package keeps it; the wheel (unmerged `tools/build_wheel.py`) must put it in `prismrt/resources/shaderball`.
- **After 5b's first stage: Hydra renders through `Session` and shares the revision mechanics with `Scene`, keeping its own scene path** (João's choice; the translator of Hydra edits into `Scene` edits, 5b's stages 2-4, is not done, for the reasons of the 5b entry below). Three parts:
  - **A hosted session** (`src/session/session_internal.h`, internal): `detail::SessionAccess::createHosted` makes a `prism::Session` without a public `Scene`; each run renders the `SceneManager` hdPrism builds (its snapshot) into hdPrism's `ProgressiveTarget` (render buffers, refinement-tile presentation, picking frames, denoised presentation) on Hydra's render thread. The session owns what the delegate drove itself: the render device and its creation job (moved from `SceneBridge::Impl::AcquireRenderDevice`: the render thread waits on it while polling for a stop, a preference change first waits for the running creation, a failure falls back to the CPU; the delegate still prints the warnings and the device line), the progressive loop with its accumulation, and the session state (accumulations, running/converged/paused, and the progress fraction, now one function for both front ends: `detail::ProgressFraction`). Hydra keeps its render thread (`HdRenderThread`, which its host stops before every edit, with the in-loop pause) and its own convergence flag (a finished run is not converged while the scene still loads). Why the front end's thread and not the session's: the host drives the render thread, and a hand-off to another thread per `Render` call would add latency to every edit and camera move. `noteScene` stays a separate call, made where the delegate made it (under its mutex, with the snapshot it reads). `ProgressiveEngine` is no longer exported (15 symbols); the hosted session adds 10 (`SessionAccess`, `ProgressFraction`) and `SceneAccess::detached` 1, so `prism.dll` exports 503 symbols instead of 507. hdPrism includes only `progressive_target.h` (the target types), not the engine.
  - **One revision layer for what both scene paths do alike** (`src/scene/revision_parts.h`, header-only, and `src/scene/environment_cache.h`, moved from `src/hydra/`): attaching a placement as an Embree instance (by ordinal for the scene; Embree numbers the delegate's), moving it, its shading transform (`PlacementTransformOf`: two copies before, Gf arithmetic in the delegate and `Matrix4d` in the scene; `Matrix4d` is bit-identical to `GfMatrix4d`, so the delegate converts and calls the same code), the light and shadow link category bits (`LinkCategories`), the rule for editing a spare revision in place (`Exclusive`: nothing but its bank holds it), and the domes' importance-table cache, which the public scene now uses too (a moved dome, or a revision rebuilt around an unchanged sky, keeps its tables; `CachedTransformedEnvironment` renders exactly as the `TransformedEnvironmentMap` the scene built, which `prism_hydra_environment_cache_test` checks). Images bit-identical. Not merged, because the two paths differ in kind rather than in code, and each is its front end's tuned behaviour: the conversion pools' keys (the scene's handles, edit versions and conversion inputs; the delegate's captured data-source handles and geometry hashes, with residency and hidden-geometry eviction on top), how the spare is brought up to date (the scene diffs its placement list against the spare; the delegate replays its dirty journal of paths, with renames and sphere batches), visibility (detach/attach by ordinal in the scene, `rtcDisableGeometry` in the delegate), lighting edits (a new revision over the shared top-level scene in the scene; applied to the spare bank, without a top-level commit, in the delegate), and the light conversion itself (`LightDesc` in the scene; Hydra data sources, Ar-resolved textures and `TF_WARN` in the delegate).
  - **An edit fuzzer** (`prism_hydra_edit_fuzz [seed] [updates]`): a seeded random sequence of transforms, visibility changes, material rebinds and light changes (sometimes two in one update) through a USD stage rendered by hdPrism and through the public `Scene`. After each update, each front end's image must equal a fresh build of the same state bit for bit (a new engine over the edited stage; a new `Scene`), and the two front ends must agree within the noise floor (their difference at most 1.25 times that of two seeds of the scene, means within 1%). Not bit for bit across front ends, for a structural reason: the delegate places every mesh through an Embree instance while the scene bakes a mesh with one instance into world space, so hits differ in their last bits and the paths decorrelate after a bounce or two (the CLI-vs-Hydra parity fixtures compare within a tolerance for the same reason). The scene's MaterialX documents are untagged, like the UsdPreviewSurface inputs the delegate converts (untagged colours do not convert, `docs/color_management.md`).
- **`prism_hydra_scene_bridge_test`'s progress-status check restores `PRISM_DISABLE_VULKAN`** instead of clearing it: in a CPU-only run (`PRISM_DISABLE_VULKAN=1`, as while GPU work is paused), the later GPU preparation preview check found Vulkan enabled and would have opened the device.
- **The shared OIDN CPU device is never destroyed** (`SharedCpuDenoiser`, `src/device/denoiser.cpp`). Its static `shared_ptr` was destroyed in `prism.dll`'s `DLL_PROCESS_DETACH`, after `ExitProcess` had killed every other thread; releasing the device terminates its oneTBB arena, which waited forever on a killed worker (a captured stack: `LdrShutdownProcess` → `prism!SharedCpuDenoiser`'s atexit destructor → `OpenImageDenoise_device_cpu` → `tbb12!wait_on_address`). About 1 in 100 CLI denoise runs hung at exit, on any device; `prism_denoise_render_vulkan_cpu` timed out once in a full ctest. Releasing it earlier needs a point every frontend (CLI, delegate, Python) reaches before exit with its threads alive; there is none in the library, and the process's exit reclaims the device.
- **SDK step 8: the wheel is assembled from the CMake build tree by a standard-library script (`tools/build_wheel.py`), not built by scikit-build-core.** The build tree already holds the package and knows every dependency root (`prism-runtime.json`, `_build_config.py`, `CMakeCache.txt`); scikit-build-core would rebuild the whole renderer in an isolated build per wheel and still not bundle the DLLs (on Windows that is delvewheel's job, and it would not see the libraries loaded by name: the MDL SDK and its plug-in, OIDN's device modules, DXC). The script walks the PE import tables (delay-loaded too) from the extensions and those libraries in the build's DLL directory order, fails on an unresolved import, a USD DLL reached from the core or a second `tbb12.dll`, and writes the wheel with sorted entries and fixed timestamps (two builds are byte-identical). No new Python tools, so nothing new in `tools/deps.json`. A scikit-build-core front end can still call the same steps when sdists or Linux/macOS wheels are wanted.
- **Wheel version `0.2.0a9`, from `python/prismrt/_version.py` only** (`prismrt.__version__` imports it, the script reads it; replaces `0.2.0.dev0`). `0.2.0aN` is the pre-release tag `v0.2.0-alpha.N`; counting one tag per landed step (alpha.1 = step 1, 5a and 5b apart, alpha.8 = step 7), step 8 is alpha.9. João creates the tags; if his numbering differs, only that file changes.
- **USD in the wheel: the existing USD build, bundled as it is (option (a)), not yet the namespaced one of 2026-10-27.** All of its libraries (USD loads plug-in libraries by name), `lib/usd` resources and the `usdShaders`/`sdrGlslfx` plug-ins go into `prismrt/usd/`, whose DLL directory only `prismrt.usd` adds: `import prismrt` loads no USD (the test checks it). `prismrt.usd` keeps step 7's check: an imported `pxr` of another build is refused before `prism_usd.dll` loads. Limits until the namespaced build: no `pxr` of another build in the same process (`usd-core`, DCCs), a `PXR_PLUGINPATH_NAME` naming another USD's plug-ins reaches ours, stages pass as files. Remaining packaging item: OpenUSD built with `PXR_SET_INTERNAL_NAMESPACE` and a library prefix (`tools/build_deps_local.ps1` options, `prism_usd` and `_prism_usd` linked against it, a second USD prefix under `D:\prism-deps`), estimated 1-2 days including the rebuild (about 2 hours on this machine), the CMake split (hdPrism keeps the host USD) and the tests.
- **The wheel ships `vulkan-1.dll` and the MSVC C++ runtime** (as `tools/package_windows.ps1` does): `prism.dll` imports the Vulkan loader, so without it `import prismrt` would fail on machines without a GPU driver; `msvcp140.dll` is neither in Windows nor in Python. Both are loaded from the package (`os.add_dll_directory` directories come before System32) unless already loaded; the older-`msvcp140` check of step 7 stays. `dxil.dll` is not shipped (2026-10-27; SPIR-V needs no signing).
- **The MDL SDK is loaded by full path first in a wheel**: the renderer loads `libmdl_sdk.dll` and `nv_openimageio` by name with `LoadLibraryA`, which ignores `os.add_dll_directory`; `_dll.py` loads the package's copies first, so the by-name loads find them whatever `PATH` or `MDL_SDK_ROOT` say. MaterialX libraries, the MDL path and DXC default to the package's (environment variables set only when unset; `Renderer(env=False)` also gets the package's MaterialX libraries). Caches stay at `RendererOptions`' default, `%LOCALAPPDATA%\PrismRT\cache`.
- **Licence files for the wheel not found on disk were fetched from upstream into `tools/licenses/`**: DXC (LLVM/NCSA, `microsoft/DirectXShaderCompiler` LICENSE.TXT), OpenSubdiv 3.6.1 (its tag's LICENSE.txt; the install has none), the Vulkan loader (Apache-2.0, `KhronosGroup/Vulkan-Loader`). The others come from the dependency installs (vcpkg's `copyright` files for OpenImageIO, OpenColorIO and their dependencies; all of the build's ports are listed, a superset).
- **SDK step 7: the Python package `prismrt` is two nanobind extension modules and a pure-Python layer.** `prismrt._prism` links `prism.dll` with the static `prism_gltf`, `prism_obj` and `prism_io` (no state of their own); `prismrt._prism_usd` links `prism_usd.dll` and is imported on first use of `prismrt.usd`, so `import prismrt` loads no USD. The C++ side is a thin 1:1 binding (one class per C++ class or struct, snake_case fields, structs constructible from keywords); keyword arguments for the descriptions, names, `scene.params`, `Scene.from_dict`/`to_dict`, the logging bridge and the `atexit` hook are Python (`python/prismrt/`), so they need no C++ and stay easy to change. Adopted from the Mitsuba 3 comparison (`local/reports/mitsuba_python_api.md`): from_dict with references by name (forward references resolve) and the key path in error messages; a traverse-like `params` mapping whose setters call the matching update and whose `update()` commits; `name=` on every `add_*`; `Image` with `__array__`/`__dlpack__`, `Image(array)`, `Image.write`, reprs; tuples and lists for vectors and matrices; `translate`/`rotate`/`scale`/`look_at` as NumPy 4x4; no variants, global state, Dr.Jit, plugin registry or integrator/film objects; exceptions that also derive from the matching builtin (`InvalidArgumentError` is a `ValueError`, `NotFoundError` a `LookupError`, `UnsupportedError` a `NotImplementedError`, `OutOfMemoryError` a `MemoryError`); `prismrt.render(...)` and per-call `samples=`/`seed=`.
- **Names are unique per scene, across kinds** (auto names `<kind><n>` for unnamed objects), so a handle-or-name argument and a `params` key (`<name>.<field>`) are never ambiguous. Enum members keep the C++ names (`Aov.PrimId`, `LightShape.Rect`); every enum argument and field also takes its name as a string, case and underscores ignored (`"rect"`, `"lat_long"`), and AOVs their Hydra tokens (`"primvars:st"`).
- **`Session.render()` raises `InvalidArgumentError` while the scene has uncommitted edits** (`allow_uncommitted=True` renders the last committed revision, as the C++ session does). Mitsuba silently renders the old values until `update()`; a batch render missing the user's last edits is the more surprising failure. `start()` does not raise: a progressive session takes the next commit by design. For this the public `Scene` gained `pendingEdits()` (the `DirtyKind` bits since the last commit; a cancelled commit leaves them), a three-line addition. Camera edits are immediate in the C++ scene and so never pending.
- **`Scene::commit()` and `prism::usd::Load()` bind the scene's renderer logger on the calling thread.** They used the caller's binding (the CLI binds its renderer's logger on its thread), so a commit on a thread without one (Python commits on a worker thread) sent IES and material warnings to the process default logger instead of the renderer's sink. No effect on images (checked bit-identical) or on the CLI (the same logger).
- **Blocking calls run on a C++ thread; the Python thread waits in 100 ms slices** (`std::thread` plus `std::packaged_task` in `python/src/common.h`): signal handlers only run on Python's main thread, so a render blocking that thread could not see Ctrl-C. Between slices the binding takes the GIL and calls `PyErr_CheckSignals()`; on `KeyboardInterrupt` it cancels (`Session::cancel`, or a commit's progress callback returning false), joins and re-raises. This thread waits; it does no rendering (render parallelism stays `tbb::parallel_for`). Callbacks take the GIL on the C++ threads, return false when the interpreter is finalizing, and an exception in one cancels and is re-raised by the blocking call or `wait()`. Every session call releases the GIL, and destroying a session releases it before joining, so a session thread waiting for the GIL in a callback cannot deadlock. An `atexit` hook cancels and joins all running sessions.
- **nanobind 3.1.0 from PyPI into a versioned prefix** (`pip install --no-deps --target D:\prism-deps\nanobind-3.1.0 nanobind==3.1.0`, `nanobind_DIR` from `cmake/PrismLocalDependencies.cmake`), recorded in `tools/deps.json` (with pytest 9.1.1; `tools/check_deps.py` checks docs/python.md). vcpkg's `nanobind` port (the same 3.1.0 at our baseline) depends on vcpkg's `python3` port, which would build another CPython than the 3.11 the build and USD use. `PRISM_BUILD_PYTHON` defaults to ON when nanobind is found, OFF otherwise (a status line says why), so machines without it build as before; its tests are registered only when it is built.
- **No stable ABI yet**: nanobind's linked stable ABI needs CPython 3.12 or later (its new split mode reaches 3.10 through a separate backend package), and the build's Python is 3.11, so the modules are `cp311`. Revisit with the wheels (step 8).
- **DLLs from the build tree without PATH**: CMake writes `_build_config.py` per configuration (copied into the package by the configuration that builds `_prism`) with the directories of `prism.dll` and its dependencies, which `prismrt/_dll.py` adds with `os.add_dll_directory`. Windows searches those directories in an unspecified order, and the first build loaded Embree's `tbb12.dll` (2021.11) instead of oneTBB's (2022.2), which `prism_usd.dll` failed on ("procedure not found"); `_dll.py` now preloads, by full path, the first directory's copy of every DLL found in more than one, as `PATH` order would. `import prismrt` also refuses an older `msvcp140.dll` than the build's toolset needs when one is already loaded (PySide6's 14.29), with the import-order advice.
- **`prismrt.usd.load(scene, stage)` does not use `UsdUtils.StageCache` for an uncached stage** (deviation from `docs/sdk_design.md` 6.5). Inserting a Python-opened stage hands its ownership to the cache (USD's Python bindings keep only a weak pointer), so erasing it after the load closed the caller's stage (checked with pxr alone). A stage already in the cache loads by its id (the 6.5 path; the caller owns the entry; `load_cached(scene, id)` too); any other loads through a second `UsdStage` over the same open root and session layers, found in the layer registry with their unsaved edits. Not carried over: the original stage's population mask and load rules. Importing `prismrt.usd` after `pxr` checks the version and that the process's `usd_usd.dll` is the one `prism_usd.dll` links, before `prism_usd.dll` loads (it would reuse an already-loaded `usd_usd.dll` of another build and crash). The packaged module will use a private USD (2026-10-27), which drops in-memory stage sharing.
- **Python default device `auto`** (2026-10-27); the Python tests render on the CPU and run with `PRISM_DISABLE_VULKAN=1` and `Renderer(disable_vulkan=True)`, because `Renderer.devices()` creates each device to list it. The Vulkan test (`prism_python_render_vulkan`) carries the `gpu` label and lock. Test labels are now appended (`cpu`/`gpu` plus `python`).
- **Python-vs-CLI parity needs the CLI's defaults that differ from `RenderSettings`**: the CLI clamps sample radiance at 10 by default (`--max-sample-radiance`), `RenderSettings::sampleClamp` defaults to 0 (CornellBox differed by 0.49 NRMSE until the test passed 10); and the CLI lights scenes without lights with usdview's default dome (`prismrt.usd.default_dome_texture()`). Left as they are (changing either default changes images); documented in `docs/python.md`.
- **`prismrt.__version__` is `0.2.0.dev0`** until the 0.2.0 release (the alpha tags are João's). Superseded by step 8: `0.2.0a9`.
- **SDK step 6: `prism` and `prism_usd` are shared libraries with explicit exports, not export-all.** `include/prism/export.h` defines `PRISM_API` (the public API: `Error`, `Renderer`, `Scene`, `Session`, `Image`, `RenderResult`, `Limits`, `RendererOptions`, `DefaultCacheDirectory`, `AovName`/`AovFromName`) and `PRISM_USD_API` (`prism::usd::Load`, `CameraFromGf`, `LoadCamera`); `src/internal_export.h` (not installed) defines `PRISM_INTERNAL_API` / `PRISM_USD_INTERNAL_API` for the internals hdPrism, the CLI and the tests still use (devices, `RendererContext`, `ProgressiveEngine`, `SceneAccess`, colour management, the texture service, the MDL compilers, the material service, render products and so on). The list came from the link errors of every consumer: 408 internal and 98 public exports in `prism.dll`, 35 internal and 12 public in `prism_usd.dll`. Everything else is hidden, also on Linux/macOS (`CXX_VISIBILITY_PRESET hidden`, `VISIBILITY_INLINES_HIDDEN`; not built here). Why not `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS`: it would export tens of thousands of template instantiations, does not export data, and hides nothing on the other platforms; the internal list is meant to shrink once Hydra renders through the public `Session`. C4251/C4275 are disabled in `export.h` (same toolset on both sides); no other warning is silenced.
- **Header-only state moved into the libraries.** Function-local statics and inline/thread-local variables in headers would give each module (core, `prism_usd`, hdPrism, the CLI, a test) its own copy, silently. Moved behind exported functions: the progress binding (`Progress::Current/Exchange`), `ErrorMaterial::Shared`, `PreparationAdmission::Shared`, the material-resource registry, the temporary-file serials (one `NextTemporaryFileSerial()`; two modules publishing one artifact could otherwise pick the same temporary name), the MDL texture runtime's per-thread shading point (`NativeTextureRuntime::Thread()`; a test that shaded through an inline `MDLMaterial` call would have set its own copy) in `src/module_state.cpp`; the material service's template and captured-material registries in `src/usd/usd_module_state.cpp`. Left as they are: immutable function-local constants (token and extension sets), the environment-settings cache in `render_defaults.h` (read-only after the first read), and `render_profile.h`'s counters (nothing sets them). `prism::Error` has an out-of-line destructor so its vtable and type information live in the core.

- **SDK step 5b stopped after its first stage: incremental `Scene::commit()` is in the core; the Hydra delegate still builds its own snapshots.** The plan was four stages (core commit; Hydra placements, materials and lights as `Scene` edits; structure and prototypes; Hydra through the public `Session`). Stages 2-4 are not started, so the old `SceneBridge` path covers all of Hydra, unchanged. Why: the delegate's snapshot and bank machinery (about 4,000 lines of `scene_bridge.cpp`) is keyed on Hydra identities that the public scene does not have: captured data-source handles as conversion keys, `SdfPath` dirty journals with structural renames and native-prototype roots, the canonical prim-id registry, instancer topologies for picking, sphere batches by path, hidden-geometry eviction by prim path, the camera-motion lighting deferral. Turning the observer into `Scene` edits means expressing each of these through the API (or adding Hydra concepts to it) and replacing the snapshot build and update functions, a rewrite of the delegate's scene path rather than a move, and the bridge tests that assert that pipeline's counters (`reusedSnapshotBuilds`, spare installs and discards, structural leaf updates, sphere-batch fallbacks) would be rewritten with it. What the core still needs before the translator: a hidden-geometry budget (`SceneOptions`), batched spheres from many sphere instances (or a `SpheresDesc` per batch, as the delegate batches), per-instance ids and user data the delegate maps back to paths and instancer chains (`InstanceDesc` has the fields), light linking from collections turned into categories by the translator, the environment cache's importance-table reuse across revisions, render settings per session (below), and a path-to-handle table in the translator that turns dirty paths into edits. Recorded in `docs/sdk_design.md` (step 5b status).
- **The core keeps two revisions, as the delegate keeps two banks.** The published revision and the one before it (the spare). A commit updates the spare in place when nothing holds it (no session renders or picks it: `use_count` of the revision and of its top-level scene) and it places the same instances in the same order; otherwise it builds a new revision. Lighting-only commits (lights, environments, a new working space) build a new `SceneManager` that shares the published revision's top-level Embree scene and copies its maps, so the acceleration structure is not rebuilt. Mesh conversions (with their Embree geometry and prototype scenes) are pooled by their inputs (`ShapeKey`: mesh and its edit version, displacing material, slot materials, subdivision level, instanced or baked into world space with the world's bits), sphere prototypes by spheres and version; revisions hold them, the pool holds weak references. Materials compile once per description, as before. Why: what the delegate's banks, prototype pool and residency reuse do, in terms of handles; the in-place path is taken only when its result is the full rebuild's (same placement ids), which `prism_scene_incremental_test` checks bit for bit after each kind of edit.
- **Embree geometry ids are placement ordinals.** Mesh placements in instance order, then sphere placements (the order of the full rebuild before), attached with `rtcAttachGeometryByID`; a hidden instance keeps its id unattached. A shared world-space mesh's geometry is attached to every top-level scene that places it (`Mesh::createEmbreeGeometry` creates it without attaching). Visibility is detach/attach rather than `rtcDisableGeometry`, which would hide a shared geometry in every revision. Scenes without hidden instances get the same ids as before (images bit-identical).
- **Hidden instances keep their conversions and count as placements of their mesh.** A mesh with one visible and one hidden instance is now placed as Embree instances, not baked into world space as a single placement, and hidden meshes are converted at commit. Why: showing or hiding an instance must not reconvert meshes (the delegate also keeps hidden prototypes). Only API users that hide instances see it (none of the loaders hides instances); their images can change by rounding.
- **A commit without edits publishes nothing** (same revision, sessions do not restart); `CommitResult` reports the edits' kinds (`DirtyKind`, the delegate's kinds with lights and environments apart) and the work (materials compiled, meshes converted or reused, placements attached or updated in place, shared acceleration, reused revision, lighting rebuilt). Diagnostics are those of the work a commit did (a reused conversion does not repeat its warnings). The grey of geometry without a material is one per scene, so revisions agree on it.
- **Render settings stay on `SceneManager`** (deferred a third time, 2.7): revisions did not change how settings reach the devices, and per-revision settings only pay off once Hydra renders through `Session`, which did not land.

## 2026-10-28
- **SDK step 5a: the progressive loop is a core engine that both the delegate and the public session drive.** `SceneBridge::Render`'s pass loop, previews, adaptive publication, denoise interval and GPU preparation preview moved unchanged into `prism::session::ProgressiveEngine` (`src/session/progressive_engine.*`); the outputs' storage and control are a `ProgressiveTarget` (the delegate's render buffers with their refinement-tile and denoised presentation; the session's host films). Hydra images stayed bit-identical (12 Hydra renders with product AOVs, denoise, adaptive and a time sample, 3 CLI renders) and its render statistics keep their keys.
- **Hydra drives the engine, not a public `Session`.** A `Session` renders a public `Scene`; the delegate still builds its own `SceneManager` snapshots until incremental commit (step 5b). Wrapping the snapshots in a `Scene` now would have been a throwaway adapter; the delegate keeps its device creation, snapshot capture and `HdRenderThread` control, and the engine is the shared part.
- **A progressive session holds its scene's render lock across passes and yields.** `detail::RenderLock` counts waiters; at each pass boundary the session lets a waiting render (another session's) or `commit()` go first. `commit()` now swaps the revision under that lock and revisions are shared, so a session keeps rendering (and picking) the revision it took and starts a new accumulation on the next one at a pass boundary. A session whose scene settings another session changed re-applies its own and resumes its accumulation. `prism_session_progressive_test` checks batch renders and commits beside a running progressive session (with other settings) and two progressive sessions of one scene.
- **Render ETA from recent pixel-samples.** The engine measures each pass (trace to commit) with the pixels it traced, and estimates the time left as (target − completed passes) × the pixels adaptive sampling still traces, divided by the pixel-samples per second of the last four passes, capped by the time limit's remainder; -1 before two passes or while preparing, 0 once complete. Elapsed time counts the preview and passes of the current accumulation, not loading or device preparation. Counting pixel-samples rather than passes keeps the estimate from overshooting when adaptive sampling thins later passes; it still assumes the remaining pixels cost what the recent ones did.
- **`pause()` stops the run and keeps the accumulation**, rather than the delegate's in-loop pause: a paused session then holds no scene lock and no thread work, and `resume()` continues from the committed passes (the abandoned pass is redone). The delegate keeps Hydra's in-loop pause (denoising the paused image). Progress callbacks run on the session's thread at pass boundaries (at most 10 Hz) and once at completion; there is no progress during device preparation yet. `render()` and `prepare()` throw `InvalidArgument` while a progressive render is running or paused.

Unset, it changes no image.

- **EON's compensation is repaired only where it renders**: OpenPBR surfaces with a constant zero `base_diffuse_roughness` (the default) keep the library graph (libbsdf adds the lobe only above zero), so their images and program sharing are unchanged; a zero roughness is structural in material templates.
- **Undeclared shader inputs**: `open_pbr_surface`'s geometry inputs under `standard_surface`'s names are renamed (Typhoon renders `openPbr_bump_fractal`'s bump); other undeclared inputs are dropped with a warning rather than failing the material. `UsdPrimvarReader_matrix` (no MaterialX definition) becomes its fallback constant with a warning rather than the error material.
- **`UsdRenderSettings.renderingColorSpace` is honoured as the working space; the default stays ACEScg** (João's decision; Typhoon defaults to `lin_rec709_scene`). Precedence: `--working-space` > `prism:colorManagement:workingSpace` > `renderingColorSpace` > ACEScg, in both loaders. USD's linear names resolve through the OCIO config's aliases. **`data` (and `raw`, `identity`) render in linear Rec.709**: Typhoon says `data` "bypasses source color transforms"; PrismRT has no transform-free mode, and linear Rec.709 is where USD's untagged values and light colours live, so they reach the image as authored, the closest sound match; explicitly tagged inputs still convert (a raw mode would need the texture service, light and MaterialX paths to skip conversion, not worth it for a debugging setting). A non-linear or unknown token keeps ACEScg with a message rather than failing: the attribute is shared with other renderers.
- **The Metal device denoises with OIDN's own Metal device** (`oidnNewMetalDevice` on the render device's `MTLCommandQueue`, `oidnNewSharedBufferFromMetal` on the denoiser's shared, hazard-tracked `MTLBuffer`s), mirroring the Vulkan structure: a resolve kernel turns the accumulation into packed RGB colour/albedo/normal on the GPU, OIDN filters there, the host reads only the denoised colour; host images (the delegate) are written into the same buffers. Same library and weights as the CPU device, OIDN's own albedo/normal prefilters. The resolve kernel is a few lines of Metal Shading Language compiled at run time (`newLibraryWithSource`), not HLSL through DXC and Metal shader converter: no descriptor heap or cache for one tiny pass. Falls back to OIDN's CPU device on host copies when OIDN has no Metal device (logged once). Written on Windows, unbuilt: docs/gpu_devices.md has the Mac checklist.
- **OIDN on macOS is built from source with its CPU and Metal devices** (`tools/ci/build_oidn_macos.sh`, the same pinned source; ISPC 1.30.0's macOS universal tarball pinned as `oidn.ispc_macos_sha256`), against the oneTBB PrismRT links, as on Windows. OIDN's Metal device is off by default (`OIDN_DEVICE_METAL`), so a stock build or a package without it would leave the Metal device on the CPU fallback.
- **The CLI's `--env FILE` follows UsdLux** (radiance = texel × 2^`--env-exposure`), matching an untransformed DomeLight of the file at intensity 1, instead of the original `EnvironmentMap`'s extra factor of two (measured: exactly 2.0x the dome). `--env` renders are half as bright as before; `--env-exposure 1` reproduces an old render. `--env-color`, USD domes (CLI and Hydra) and the default dome already followed UsdLux and are unchanged. `EnvironmentMap` has no default multiplier any more, so no caller can pick up the factor by omission.
- **vk_oidn from NVIDIA's prebuilt SDK package, not built from source** (`tools/ci/fetch_vk_oidn.ps1`, v0.2.0 pinned with the package's SHA-256 in `tools/deps.json`), not a git submodule. Its Slang kernels need a `slangc` with `-denorm-mode-fp16` (vk_oidn's CMake checks it; tested with Vulkan SDK 1.4.363 / Slang 2026.17); our Vulkan SDK 1.4.321's `slangc` 2025.11 lacks the option, and the package needs only the Vulkan headers we already have: a static library (Release `/MD`, which RelWithDebInfo maps to) with the compiled kernels and the colour filters' weights embedded, so nothing new ships at run time. Its weights are OIDN 2.5.1's (oidn-weights 28883d17): packing our OIDN 2.5.1 source release's `rt_hdr_alb_nrm.tza` and `rt_hdr_calb_cnrm_large.tza` with vk_oidn's `pack_weights.py` gives byte-identical files to the embedded ones. The commits after v0.2.0 change only comments, docs and benchmarks.
- **The GPU prefilters the guides like OIDN's CPU device** (`prism:denoisePrefilter`, default on): vk_oidn has no albedo/normal-only filter, so the fetch script packs OIDN's `rt_alb`, `rt_alb_large`, `rt_nrm`, `rt_nrm_large` (from the OIDN source release, with vk_oidn's pinned `pack_weights.py`) and the build embeds them (`cmake/embed_files.py`); they run as vk_oidn LDR filters with custom weights: the albedo with OIDN's sRGB transfer, the normal with the linear one on `n * 0.5 + 0.5` (OIDN's own `snorm` mapping, done by a small pass before and after), the same models per quality as OIDN (`_large` for high, the base network otherwise). Without them the GPU's default output would be another image than the CPU's (prefiltering lowers the error by about 10% on the test room).
- **The Vulkan device enables vk_oidn's features only when the GPU has them all** (`shaderInt64/16`, 16-bit storage, `shaderFloat16`, the Vulkan memory model, `maintenance4`, subgroup size control; cooperative matrices when present) and otherwise falls back to OIDN's CPU device on host copies, saying so once (`PrismRT Vulkan: denoising ...`; the CLI prints the denoiser per denoise and in `[PrismProfile]`, the delegate in its `denoiser` stat). `PRISM_GPU_DENOISER=cpu` forces the fallback (and enables none of the features). The storage-image features vk_oidn's helper also sets are left off (PrismRT passes buffers).
- **Whole-image renders denoise their accumulation in place; the delegate uploads its host images.** The CLI path resolves the host-visible accumulation buffer on the GPU (sums times each pixel's 1 / samples, the same float product the host computes) into the denoiser's own RGBA buffers, denoises and reads back only the denoised colour. The delegate's accumulation lives on the host (part 1), so its denoise worker's images are uploaded; keeping progressive accumulation on the GPU is a separate change.
- **Denoising: OIDN 2.5.1 built from source with only its CPU device, against PrismRT's oneTBB** (`tools/ci/build_oidn.ps1`, pinned with source and ISPC 1.30.0 checksums in `tools/deps.json`), not Intel's prebuilt Windows package. Evidence: the prebuilt `OpenImageDenoise_device_cpu.dll` imports `tbb12.dll`, and the package ships oneTBB 2023.1 (`tbb12.dll` 2023.1.0; `oidnBenchmark -v 2` prints `TBB_header_interface_12190`); PrismRT (and OpenUSD, Embree) load oneTBB 2022.2 (interface 12160). Windows reuses a `tbb12.dll` already in the process, so the prebuilt device would run on an older runtime than its headers, which oneTBB does not support (only older binaries on newer runtimes); shipping its DLL instead would be a second, different oneTBB for the process. Our 2022.2 `tbb12.dll` does export every symbol the prebuilt device imports, so it might work, but unsupported. Built here: three DLLs (`OpenImageDenoise`, `_core` with the weights, `_device_cpu`), no `tbb*.dll`; the package script refuses one beside them and checks the package holds exactly one `tbb12.dll`. Optional at build time (`PRISM_ENABLE_OIDN`, ON when found). Our MSVC build runs as fast as Intel's (1080p high quality: 398 ms against 376 ms in OIDN's benchmark on this machine). Also checked: Intel's prebuilt DLLs with our 2022.2 `tbb12.dll` do run (436 ms), which is the unsupported combination we avoid.
- **The denoiser is the render device's** (`RenderDevice::CreateDenoiser`, `ImageRequest::denoise`): frontends never pick a backend, so vk_oidn (part 2) and OIDN's Metal device (part 3) replace the CPU fallback inside the devices. Whole-image renders denoise where the accumulation lives (the device, at the end of `RenderImage`); the delegate's progressive accumulation is on the host, so it hands host images to the device's denoiser.
- **The denoising normal is the shading normal at the albedo's vertex** (world space, through sharp bounces like the albedo, averaged over the pixel's samples), a fifth light AOV channel, not the geometric `normal` AOV (pixel-centre hit only: aliased, and not through glass). It rides in the `w` of the GPU's existing light AOV entries: no new storage, and renders without light AOVs are unchanged.
- **`--denoise none|aov|replace` in the CLI; `prism:denoise` true means `replace` there and "show the colour denoised" in the delegate**, whose raw accumulation (what `Map` and the colour products read) stays untouched. A `denoised` AOV/RenderVar is always denoised. Turning `prism:denoise` on or off restarts the accumulation (guides from its first sample); quality, prefilter and interval changes resume it.
- **The delegate denoises on its own worker thread** (one `std::thread`, coordinating only; OIDN's CPU device runs on the process's oneTBB): the render worker copies the means every `prism:denoiseInterval` passes and publishes finished denoises at pass boundaries, so it never waits for one, except for the final denoise at convergence, where it polls a stop every 2 ms.

## 2026-10-26
- **UsdLuxShapingAPI follows the 26.08 schema text literally** where it is precise: the cone, softness, focus and IES factors multiply; an applied API's fallbacks apply (the 90 degree cone limits sphere and cylinder lights to the front hemisphere); IES intensities are in candela without `normalize` (as the schema's formula reads), divided by the profile's mean intensity with it (the schema writes a product but says it preserves energy). Distant lights and domes ignore shaping. Shaping data rides in the light-alias buffer after the alias entries (no new binding, no larger `LightRecord`); IES profiles are resampled to 1-degree grids rather than kept on the file's angles (O(1) lookups; exact where the file's angles are whole degrees).
- **Motion blur waits until the SDK and Python API exist.** It changes how scenes are represented (time samples, velocities, shutter) in the layer the SDK will reshape, so it is built once on the SDK; the SDK design reserves time-sampled data, a shutter interval and per-sample time so adding it doesn't break the API. Next is Phase 8a (spotlights and IES), then the SDK.
- **The CLI compiles USD materials through the delegate's material service** (folded parameters, templates, caches), so both front ends share one material path and load at the same speed.
- **Surface repairs rewrite a private copy of the library graph, not the material** (`ClonePrivateGraph`/`PublishPrivateGraph` in `src/materialx/loader.cpp`): flattening the surface into the material made its internal constants (scatter modes included) class parameters, so the CLI's unfolded class programs kept every lobe variant (OpenPBR glass 3.5x, thin walls 7x the library's SPIR-V; cold Vulkan 412 s). A content-named nodedef and graph keep the constants literal and the node's inputs as the parameters, and are shared by every material with the same repair. Chosen over folding the CLI's parameters (that would end the CLI's program sharing across variants) and over a hand-written MDL implementation per repair (a second copy of each library graph to maintain). Float-level differences only (constant folding): albedo test values equal except 1e-4 in two tinted, sampled cases.
- **A thin wall whose backface shader is its surface compiles its scattering once** (equal slot hashes; CPU index and GPU dispatch alias the surface's function, from the surface's call site because DXC inlines each call): the second copy made thin-walled programs 1.9x larger. Identical code, identical images.
- **Vulkan shaders are checked and budgeted before the driver compiles them** (`PRISM_VULKAN_MAX_SPIRV_MIB`, `PRISM_VULKAN_DRIVER_MEMORY_MIB`): the driver's compiler runs in our process and ends it when it runs out of memory (OpenPBR playground: "LLVM ERROR: out of memory" with 16 large callables compiling at once), so concurrent DXC and driver compiles share a memory budget estimated from the shader sizes, and a shader too large for the machine falls back to the CPU device with a message instead of being handed to the driver. Slower cold compiles of scenes with very large programs (OpenPBR: 23 minutes under a 24 GB cap) are accepted over crashes; shrinking those programs is left for later.
- **Large MDL programs are two Vulkan callables, sample and evaluate** (`PRISM_VULKAN_SPLIT_PROGRAM_KIB`, default 1536 KiB of generated code): the driver's compile memory grows with the square of the SPIR-V size, so OpenPBR's 15 MB glass programs as 9 + 6 MB parts compile several at a time (cold OpenPBR 1468 s to 412 s, the same image). Small programs stay whole because a split program runs its MDL init twice when it evaluates (OpenPBR GPU time 0.83 to 0.96 s for 16 spp). The dielectric repair was left as is: none of the playground's programs uses `prism_dielectric_split`; its large programs are the coupled RT glass itself.

## 2026-10-25
- **Light AOVs split the colour by the first scattering vertex** (Cycles'/RenderMan's per-lobe convention, `C<RD>.*` / `C<RS>.*`): `emission` = light seen before any vertex (dome included, so the three add up to the colour without a fourth AOV); `diffuse` = MDL's `bsdf_diffuse` part at that vertex (diffuse transmission included) and subsurface entries; `specular` = the rest (glossy, delta, glass of any roughness). The split is the expected value of the lobe fractions of the sampled direction (the Phase 4 light-lobe machinery), not the sampled lobe's event type, so it needs no new MDL output and holds for MDL's stochastic lobe selection. LPEs other than the beauty's stay unsupported.
- **The albedo AOV is a per-sample estimate** (the BSDF sample weight) at the first non-sharp vertex, not MDL's auxiliary albedo function (no new generated code; converges with the samples; exact for Lambertian). "Sharp" = delta or BSDF sample pdf ≥ 1000/sr: MDL reports smooth OpenPBR glass and mirrors as glossy lobes, not specular events. Escaped paths give 0.
- **GPU cost is a kernel variant** (`PRISM_LIGHT_AOVS`), compiled the first time a render asks for light AOVs, so renders without them keep their kernel and images; the CPU checks a flag per contribution.
- **`Pworld` is the world-position AOV name** (`P` accepted as an alias, as RenderMan and Cycles call it); multi-part EXR is opt-in per product (`bool prism:exr:multiPart`), the default stays one part with every layer.
- **A thin-walled material whose back face emits what its front does is not a varying emitter when the front's emission is zero, and a varying cutout does not make zero emission vary** (`MDLMaterial::evaluateUniformEmission`, `backface_emission_matches_surface` from the compiled slot hashes). The CLI compiles each material as a class (parameters stay arguments), so the SDK cannot prove a thin-walled material's back face dark, and about 20 of the OpenPBR playground's materials counted as varying emitters (14 of them thin-walled): together with the real ones they went over the 2^20-triangle budget, so no varying emitter was a light and MEET MAT (a textured emitter) was only found by BSDF sampling. The delegate folds parameters and was under budget (225k triangles). Class compilation stays (templates need it); images of scenes under the budget do not change (chess, egg_gold, Teapot are bit-identical). `PRISM_MAX_VARYING_EMITTER_TRIANGLES` lowers the budget (for the `mtlx_emission` parity fixture), and going over it now prints a warning.
- **The CLI shares the delegate's mesh conversion and UsdPreviewSurface rewrite** (phase 7): `src/mesh/mesh_conversion.cpp` (subdivision, displacement, refinement budget, triangulation) and `src/materialx/preview_surface.h` were moved out of the delegate unchanged; each loader still reads the stage its own way (UsdGeom in the CLI, scene indices in the delegate). The CLI keeps its own polygon conversion for meshes that do not refine or displace, so its earlier images stay bit-identical; refined and displaced meshes use the shared one.
- **The CLI places every gprim on its own** (phase 7), as the delegate does, instead of one merged mesh: needed for light-link masks, instance primvars, per-prim primvars and ids. Polygon meshes stay in world space (bit-identical to before), prototypes are Embree instances.
- **The CLI reads USD materials from the composed UsdShade network first** (as the delegate), falling back to reading a referenced `.mtlx` file directly only when no network is composed: the direct read failed on the Teapot (material names) and the OpenPBR playground (relative texture paths in string MDL modules).
- **CLI fallback grey is the delegate's 0.5** (was 0.7) for geometry without a material or `displayColor`.
- **Prim ids are compared up to a renumbering** (`prism_compare_images --relabel`): each loader numbers its prims; element and instance ids compare exactly.
- **Textured emitters (Phase 5): the light sample looks the emission up with the footprint of the BSDF ray in its direction**, not at the finest texture level. MIS needs both strategies to estimate the same integrand; with the finest level, texture filtering of BSDF hits made the checker fixture's floor 6–10% too bright where black and bright texels meet.
- **Varying emission includes directional and cutout emission**, not only textures: a coated OpenPBR emitter (directional EDF) or an emitter with a varying cutout is now a light whose emission the light sample evaluates, instead of being left to BSDF sampling. Images of such scenes change (less noise; same expectation).
- **Triangles whose estimated emission is zero get no light record** (BSDF sampling only, still unbiased); a material's emission counts as zero when it is zero at the centres of up to 64 of its triangles on a placement. This probe also decides `SceneHasEmitters` (the default dome rule), so both agree. Other triangles weigh at least 10% of their material's mean.
- **Large light tables (over 4096 entries) pick lights with the white noise**, not the low-discrepancy selection number: on its 24-bit grid that number cannot select among a million entries with the table's probabilities, which biased MIS (pre-existing with many constant-emission triangles; OpenPBR's string lights). Scenes with such tables change (OpenPBR CLI mean −0.5%, closer to a BSDF-only reference); smaller tables keep their images bit for bit.
- **The estimate is capped** (2^20 triangles, about 4M evaluations: 1 to 16 stratified points per face) and reruns at each scene change; no cache yet.
- **CI paused until the repository goes public.** GitHub Actions stopped on billing; public repositories get free minutes.
- **UsdPreviewSurface rough glass is left as MaterialX builds it** (rough specular over smooth transmission). The UsdPreviewSurface spec says "the transmissive lobe (if any) always assumes roughness 0.0", so the alternatives that conserve energy (one rough lobe: frosted; a smooth lobe: drops the specular roughness) contradict it. The remaining energy loss is MaterialX/MDL's to fix. Comparison: `local/comparisons/usdps_glass/`.
- **The opaque layering loss (~4.6%) is not repaired.** No MDL construct reproduces OpenPBR's energy-conserving layering; a diffuse scale-up would be wrong at grazing angles and change nearly every material. Upstream only.
- **MaterialX upstream reports are held back** for now (list in the session memory; drafts in `local/upstream/`).
